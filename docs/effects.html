react-game-engineAuthoring guide and reference

Effects and audio

State is for what lasts. A burst of dust where you landed, or a sound, happens at a moment and then plays out. For those, make a store once, mount its renderer once, and call it from anywhere, the way a toast library works. There is no useEffect.

  • A burst belongs to the layer, so it plays out even if whoever asked has left. With no layer mounted, it is counted but not drawn.
  • A preset is <Particles>'s props except rate, emitting and space.
  • A sound with once: true plays at most once a step however many components ask for it: twenty towers firing together make one shot, not a roar.
  • Continuous effects (a trail while dashing) stay JSX: <Particles emitting={dashing} space="world" />.

Motion: springs and tweens

  • Each follows its target: change the target (from state or props) and the value moves to it. Both start at their first target, without moving.
  • useSpring is set by duration (about the seconds it takes to settle, default 0.5) and bounce (0, the default, for no overshoot, up to just under 1 for a lot of it). A new target keeps the speed it had, so it turns round smoothly.
  • useTween takes duration (default 0.25) and ease: linear, inQuad, outQuad, inOutQuad, inCubic, outCubic (the default), inOutCubic, inSine, outSine, inOutSine, inBack, outBack, outElastic, outBounce, or a function from a .ts file. A new target starts again from where it is.
  • They step in the component's useUpdate: they follow the fixed step, freeze and replays, render only while moving, and keep their place through a hot reload. They also stop while <Game paused> is on, so a pause menu does not animate.
  • Each takes a number: a point is two springs, one for each axis. In plain code, stepSpring and stepTween (from @rge/runtime) take points too.
  • transform={{ opacity }} fades anything and what is in it; see Transforms.

Music and fades

Freeze frames, shake, squash

Kite also uses <Particles> directly: room-wide drifting dust (width, height, prewarm, space="world") and dash sparks (emitting={body.state === "dash"}); and a list of ghost Sprites in state, with falling opacity, for the dash trail.

  • freeze(steps), called in a handler or in plain TypeScript (Kite calls it from playEvents), skips every useUpdate for that many steps (a hit, a dash). useInput keeps running, and a press during the freeze is kept for the first step after.
  • useShake() and useSquash() are state: see Custom hooks.

Layers, light and blend modes

A <Layer> draws its children off screen, into a picture the size of the screen, and then lays that picture over what is under it with a blend mode. That is how a cave goes dark and a lantern lights it again: a layer of near-black, multiplied over the world, with lights added into it where they shine.

  • blend is how the layer meets what is under it: "normal" paints over; "multiply" shades (white leaves it as it is, black makes it black); "add" brightens; "screen" brightens but never past white.
  • childBlend is how each child is drawn onto the layer itself: "add" makes two overlapping lights brighter than one.
  • clear is what the layer holds before its children are drawn, every frame (transparent by default): the darkness of a light map.
  • opacity fades the whole layer, and an opacity above it applies to the layer as a whole, once.
  • It is drawn through the same camera as the world (or the HUD's view, inside a <Hud>), so children are placed in world coordinates as usual. It covers the screen (the game's canvas under a <Screen>).
  • Inside a layer, children are drawn in tree order: a z there is ignored, and the layer as a whole is drawn at its own z. Layers nest four deep.
  • Bramble's cave is the example: games/bramble/src/Play.tsx, its light made by tools/make-assets.ts, and its picture in stories/screenshots/Play/Cave.png.

Input actions and timing

Named actions

Name actions once and every input.pressed / down / released accepts a name as well as a key. Rebinding is one place.

  • down: any key held. pressed: one went down this step. released: one went up with none still held.
  • An unknown name warns once and lists the actions. Rebinding at run time: see Saved data. No analog axes yet.
  • Gamepad: the first pad's buttons and four directions are keys (see key names). gamepadDeadzone on <Game> sets the stick threshold.

Who hears the keys: inert and modal

Input is polled, so every useInput sees every key. Two props of <Entity>, <Flex> and <Hud> decide which subtrees hear it, as in HTML, so a component does not have to guard itself with an if (paused) return.

  • inert is the HTML attribute. In the subtree, useInput and useUpdate get no keys pressed or held, and pointers and buttons cannot be pressed, hovered, focused or reached by their pressKey. It still updates, draws and collides.
  • modal is a <dialog> opened with showModal(): everything outside it is inert, its ancestors too, and the focus stays among its buttons. If several are mounted, the one mounted last takes the input; when it goes, the one below has it again.
  • A component passes them on as it would any prop, at its root: function Menu({ inert }: MenuProps) { return <Entity inert={inert}>…</Entity>; }, then <Menu inert={capturing} />. (A state or ref cannot be named inert or modal: they are the root's.)
  • It decides who hears input, not who updates: to stop the world stepping while a pause menu shows, give the root <Game paused={paused}> (below).
  • A modal mounted during a step hears keys from the next step, so the press that opened it does not reach it. Bramble's "press a key" prompt (KeyPrompt.tsx) is a modal with no children that takes the next key.

Fixed timestep

  • useUpdate runs at a fixed rate with dt = 1 / rate. A frame runs no step, one, or several (at most 8; leftover time is dropped). Drawing stays once per frame, and nothing is interpolated.
  • No input is lost: a tap between two steps is seen by the next one as pressed and released.
  • Off by default: one update per frame with the frame's own time.

Timers: after and every

  • Statements in a handler, as setTimeout is in React. The function is a handler too: it writes state, calls actions, plays sounds.
  • A timer is the component's: it is cancelled when the component unmounts, so it never sets state on one that is gone.
  • They count game time in the update phase: they follow the fixed step and replay, and stop during freeze and <Game paused>.
  • A timer or state? A timer is code, so it is not saved and a hot reload drops it (the log says so). Use one for what is only for the eye: a flash, a blink, a beat before a title appears. A delay that is part of the game (a few seconds of safety after a hit, a slow) is state that counts down in useUpdate, or a time it ends at kept in state: it is then saved, reloaded and tested like any state.

Fast-forward and pause

  • timeScale={2} runs two steps a frame, each with the same dt: the game plays exactly as at 1, twice as fast, and a replay is the same at either speed. It costs two steps a frame.
  • paused stops every useUpdate. useInput, presses, pressKey and the focus still work, so the pause menu's buttons unpause it.
  • Unlike the other <Game> settings, these two are read every frame, so they may be state.

Seeing inside a running game

  • The layout overlay. Under rge dev, F1 in the window (<Game overlayKey> to change it) outlines every <Flex> and its padding, every collider (a colour per layer) and every pointer, and labels the box under the mouse with the components it is in, its size and what sized it (width grow). A packaged game never has it.
  • The inspector. rge dev prints an address (inspector: http://127.0.0.1:…/): open it in a browser to see the tree by component, as React DevTools shows it; the selected component's state and refs, props, the game-state paths it reads and how many times it has rendered; and each game state with its last actions and what each one changed, as Redux DevTools shows them.
  • Editing. A state value or a game-state leaf can be changed in the inspector (type a JSON value). It shows on the next render. An edit is not input, so a replay does not repeat it; the log says so each time.
  • Profiling. The inspector's profile button times every component while the game runs and shows, once a second, a table of milliseconds a frame: for each component (by name, with how many there are) its input, update and render time and renders a frame, the slowest first, and above it the frame's phases (steps, collisions, building the frame, drawing). A row over a millisecond is red. Timing costs a little, so it is on only while the button is; in a test or a tool, startProfiling() from @rge/runtime gives the same report (profiler.take()).

Rewind

Under rge dev the game records every frame's input and takes a snapshot every second, for the last five minutes. Go back to the moment something went wrong, fix the code, and watch the same moment again.

  • F2 pauses. ← and → go back and on a frame, ↑ and ↓ a second; a bar over the game shows where you are. F2 again plays on from there with live input, and the recorded future is dropped. The inspector's page has the same timeline, with a slider.
  • Going to a frame restores the snapshot before it and plays the recorded input again to it, silently and without drawing: under a tenth of a second.
  • Save a file while paused and the game is reloaded and the same input played again with the new code, to the same frame: you see the moment with the fix.
  • F4 saves the moment (from the snapshot before the paused frame to it) to moments/. A test plays it again with replayMoment from @rge/player: the bug becomes a replay test.
  • It relies on the game being a function of its input. Each frame's state is hashed as it is played; when a replay differs from the recording (Math.random or Date.now in the game, a timer used for gameplay), rewind names the first frame that differs, in the log, on the bar and on the page.

Testing without a window

  • npm run check:kite (or check:<game>) compiles, type-checks, runs tests and replays the game headless.
  • Input scripts: right*30, jump, right*20+dash. Items run in order, + starts terms together, name*N holds N frames, a bare name taps, _ waits. A key stays held until the script changes it, so right, right is one press held for two steps, and right, _, right is two presses. A name that is neither a key nor an action throws, listing the actions. runScript steps a game and returns what you observe. A game exports bindings ({ jump: ["Z"], … }) so scripts can use action names.
  • rge screenshot <game> --script "right*30" --at 0,29 renders chosen steps to PNG through the software renderer (needs npm run native:build:headless).
  • --gpu draws them with the desktop build on OpenGL instead, as a player's window does, so what a driver (or, later, a shader) does shows. It needs npm run native:build; without a display it runs itself under xvfb-run, which Mesa's software OpenGL draws for.
  • --compare refs/ checks each frame against refs/step-<n>.png and fails if one differs; --tolerance 64 lets a channel differ by that much (two Mesa versions do), and --update writes the references. npm run check:gpu does this for the demo and Kite, and CI runs it.

Testing one component: @rge/testing

As React Testing Library tests one React component, render mounts one compiled component in a headless world, and the test steps it, presses keys, reports collisions and presses, and reads what it holds and what it would draw. A component that owns its logic is then as easy to test as a rule.

  • render(Component, props, { tilemaps, controls, dt, collisions }): the game state is put back to its start, the maps are registered, and the component is mounted. With collisions: true each step finds its own contacts, as the player does, so a component whose children collide (a battle's enemies and shots) is tested whole.
  • place({ tag, data, x, y, width, height }) puts another collider in the world, for the component to find or touch (an enemy near a tower); remove(collider) takes it out.
  • step(n) runs steps with nothing pressed; input("down, _, confirm") runs an input script, through the game's controls when given.
  • collide(tagOrCollider, { tag, data, width, height }, times) and separate(…) report contacts; press(pointerOrName) clicks a pressable in its middle; setProps(props) gives new props; unmount() runs its unmount handlers.
  • state(component?) is a component's state and refs by the names in its source; texts() the words of every <Text>; find(nameOrClass) and findAll search the tree.
  • Outside render, a whole-game test, a replay check or a balance tool reads the running game the same way: findComponent(Play) (or findComponent("Hero")) is the component in the game's tree, findComponents every match, and componentState(component) its state by the names in its source, all from @rge/testing.

Previews: one component on its own

As Storybook shows one React component with given props, rge preview shows one component of the game, without playing to where it appears. A stories/ folder beside test/ holds a file for each component: its default export says how it is shown, and every other export is a story, its props.

  • stories(Component, { size, origin, scale, background, wrap }): the screen the component is drawn on (size, in game pixels), where its own (0, 0) sits on it (origin, default the top left), how many times larger a screenshot is (scale, default 4), and wrap to put it inside something it needs, a Provider or a Flex that gives it a width. It is drawn with the game's own <Game> look: background, assets, font, text size and colour, controls.
  • story(props, { setup, input }) for a story that sets game state first (every game state is put back to its start before setup) or plays an input script before it is looked at. A plain object is just props. Stories are listed by name.
  • rge preview opens a window on the first story, with hot reload: save the component or the stories file and it changes in place. F5 and F6 go to the previous and next story; --story SidePanel (or SidePanel/Build) starts at one.
  • rge preview --screenshot stores a PNG of every story in stories/screenshots/; commit them. rge check then renders every story again and fails on a picture that changed, on a story with no picture, and on a picture whose story is gone, and says where the new pictures are. When the change is meant, store them again. This needs the headless librge, which @rge/native ships; without it the check says it did not compare.

Hearth's stories found the build menu's 2 MORTAR 80 a few pixels wider than the side panel, which the game showed cut off at the window's edge.

Saved data and settings

A save and the player's settings are kept between runs in the game's folder in the user's data directory ($XDG_DATA_HOME/<id>, ~/.local/share/<id>, or $RGE_DATA_DIR in tests). Name the folder with the id prop of <Game> (a literal: letters, digits, _, -); without it nothing is kept.

  • Component state (tree: true): an enemy that keeps its own hp in useMutable keeps it in the save. On load, apply runs first; once the tree it builds has settled, each component takes its saved state back, found by its path from the root, and a list item by its key (so an enemy removed before the save is loaded does not hand its state to the next one). Values that are not plain data (a function, a body) are left out, said once.
  • What is stored is JSON, { version, data } (and tree with tree: true). A file that does not parse is said once and read as no save; a save from a newer version than the game is refused with a message; migrate steps run in order up to the current version.
  • Settings are applied when the game starts, before the first frame, and on each set: music and effects are the two volume groups (setVolume("music", v) multiplies every <Music>; effects every sound), fullscreen switches the window, bindings goes to controls.load. Other settings are the game's own.
  • Showing them: settings and controls are not state a component reads, so settings.subscribe(fn) (after each set, reset and reload, once applied) and controls.subscribe(fn) (after each bind, reset and load) say when they change; both return the function that stops it. A component shows them with useStore(settings, read), React's useSyncExternalStore: read is a function from a .ts file that returns what to show; it runs at mount and on each notification, the component renders only when the data it returns differs, and the subscription ends when the component goes (Bramble's Settings.tsx). Underneath it is useMount returning the subscription's cleanup, which a component can also write itself. If several screens show a setting, mirror it into the game state from a .ts module instead.
  • Rebinding: controls.bind("jump", ["Space"]) (false for an unknown action or a key that is not a key name), controls.reset(), controls.toJSON(), controls.load(data) (ignores unknown actions and keys). The change applies at once. input.lastPressed() is the first key pressed this step, or undefined: "press a key for Jump" (const key = input.lastPressed(); if (key !== undefined) bindKey(action, key);).
  • Tests: setStorage(createMemoryStorage()) in a runtime test; new RecordingBackend({ storage: { save: "…" } }) starts a replay from a save, and backend.stored shows what was written.
