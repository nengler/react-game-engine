Write games as components.

A native-first 2D engine with React-like TSX authoring. There is no React and no virtual DOM: a compiler turns each component into a TypeScript class whose children are persistent instances, updated in place when state changes.

Component.tsxYour TSX: state, hooks, elements.
→
CompilerChecks the rules, lowers to an IR, emits a class.
→
Generated .tsOne class per component, committed next to an .ir.json.
→
PlayerRuns the frame loop, draws via raylib, reads input.

The mental model in five lines

  1. A component is a function: hooks, then one return of JSX. It is compiled, never run as written.
  2. Its root is a built-in (Entity, Sprite, Game…), which the generated class extends.
  3. State is written directly (s.hp -= 1), and a handler reads its own writes; render sees what the frame committed. A frame's writes cause one render.
  4. Position is state: x={s.x} y={s.y} on any built-in (transform={{ x, y }} on a component), usually driven by useMutable. Rows and columns are a <Flex>, anywhere. See Placing things.
  5. Each frame runs useInput → useUpdate → render dirty components → commit structure → draw.

Game code goes in components, as in React. An enemy keeps its own hp in useMutable, walks in its useUpdate, takes hits in its collider's onCollisionEnter and tells its parent it died through a callback prop. A plain function in a .ts file is for what you would extract in React too: a pure calculation, a table, or something a search runs thousands of times.

The rule of thumb. Anything outside the supported subset is a compiler error (RGE####), never silently ignored. See Error codes.

A whole component

Coming from React

A component reads like React, and most of what you know carries over. The difference underneath: the component is compiled, never run as written. The compiler turns it into a class whose children live for as long as it does and are updated in place, so the function body is a description the compiler reads, and it only understands the part of TypeScript it can turn into that class. What it does not understand is an error (RGE####) at build time, not a surprise at run time.

What carries over

ReactHere
Function components, props, a props typeThe same. The props type is written in the parameter (({ hp }: { hp: number })) or declared in the same file.
An early if (!hero) return null;The same, at the top of the body: each if (…) return …; becomes a condition of the last return, and what follows it is worked out only when it did not return.
useState, updaters, batchinguseMutable: state you write directly (s.n += 1), with no setters or updaters. A handler reads its own writes at once, so s.n += 1 twice adds 2; render sees what the frame committed, and any number of writes cause one render per frame. A useState is an error whose message writes out the conversion, and the editor's quick fix converts the file. Why: MUTABLE_STATE.md.
useMemo, useCallback, React.memoNot needed. The compiler knows what every value reads, so it does what they are for by itself: a derived const that calls a function is worked out again only when what it reads changes, and a render writes an element's values, or sends a child its props, only when a state or prop they read is a different value than at the last render. The component's functions are made once, so passing one down never re-renders anyone. See what a render does.
{cond && <X />}, {a ? <X /> : <Y />}, fragmentsThe same. A condition turning off unmounts.
{items.map((i) => <X key={i.id} />)}The same, with one inline arrow. Instances follow keys. key on a single element starts it over when it changes.
childrenchildren: Child in the props type, placed once as {children}.
Custom hooksThe same, written as use… functions; each call is expanded in place, so it gets its own state.
A Zustand storecreateGameState, read with useGame((s) => …) selectors and changed by actions.

What is different, and what to write instead

You would reach forWrite
useEffectThere is none, on purpose. Do the work where the change happens (an action, a handler), derive values, and use useMount, which may return a cleanup. See No useEffect.
onKeyDown, onClickKeys are polled: useInput((input) => input.pressed("jump")) every frame, and useUpdate((dt) => …) for the step. Clicks are onPress on a <Pointer> or <Flex>. inert and modal decide which subtrees hear the keys. See Who hears the keys.
style, CSS positioningtransform={{ x, y, rotation, scaleX, z, opacity }}, relative to the parent; <Flex> lays out UI.
useContextThe same: createContext in a .ts file, <Theme.Provider value>, useContext(Theme). What the whole game shares goes in useGame.
ref={…} on an elementNone: what is on screen follows state and props. useRef holds values.
Text in JSX: <p>Score {n}</p>Inside <Text>, as its children: <Text>Score {n}</Text>, or a component of your own that takes text (<Label>Score {n}</Label>, see Text wrappers). There is no text attribute.
A loop or push in the body to build a listThe same: statements in the body (loops, let, a local array) run again when what they read changes.

Three places code can go

Most "why is this an error" comes from writing code in the wrong one of these. Each is checked by its own rules.

WhereMay holdFor
The component bodyHooks, then statements that work out what to draw (derived consts, loops, let), and one return of JSX. No setters: a body describes, it does not change.Describing what is on screen, from the component's state and props.

Plain .ts filesAny TypeScript.What you would extract in React too: tables and numbers, a pure calculation (a path, a target), the game state, and code a search runs many times (Kite's solver).

The shape that works. Hearth's battle is in its components: Play keeps the gold, the lives and the lists; each Enemy, Tower and Shot keeps its own state and steps itself; they report up with callbacks and reach each other through collisions that carry data. Each is tested alone with @rge/testing. Kite keeps its movement in plain functions because a solver steps it thousands of times. See Plain functions.

When something goes wrong

Each component is written out as a class in generated/ (by rge dev, build and check; never edit it). You should not have to read it: an error names your .tsx.

WhatWhere it points
A rule of the language (RGE1xxx)The line in src/, as you wrote it (custom hooks included).
A type error (RGE9001, RGE9002)The line in src/ of the element or hook; for one found in the generated code, where it was found is added in brackets.
An error thrown while the game runs (in the window, in a test)at Main.onInput (src/Main.tsx:14:3): the component's class, the method its hook became (onInput, onUpdate, onMount, render) and the line of that hook or element. Plain functions in .ts files show their own line.

When the game does something you did not expect

What you seeWhy, and what to write
My enemy does not see the playerTwo components share a value through their common parent: the player reports where it is with a callback prop, the parent keeps it in useMutable and hands it down (a prop, or context). It arrives one step later, every time. See Sharing state between components.
My collision is a step late (the hero is inside the wall before it stops)onCollisionEnter runs after the step's updates. Move with useBody: move stops at walls, and touching and overlapping answer in the same step.
A box is not where I expect, or I cannot see what a component holdsUnder rge dev, press F1 in the window to outline every box, its padding, every collider and pointer, and name the box under the mouse; open the inspector's address that rge dev prints to see the tree, a component's state and the game state as they change. See Seeing inside a running game.
Something went wrong a few seconds ago, and is hard to make happen againUnder rge dev, press F2 and step back to it with the arrow keys; fix the code and save, and the same moment plays again with the fix; F4 saves it for a test. See Rewind.
I am building a panel or a dialogue box, and must play to where it shows each timeGive it a stories file (its props, and game state for what it reads), and rge preview shows it on its own with hot reload; rge preview --screenshot stores pictures that rge check compares. See Previews.
A child's report in a step loses all but oneSeveral children call the parent in one step, and each setList([...list, x]) starts from the same snapshot. Use an updater: setList((list) => [...list, x]).

rge turns this on for you (source maps next to each generated file, and Node's --enable-source-maps for the window and for rge check's tests). A packaged game, and the Rust host (--engine quickjs), do not map yet: their errors name the bundled game.js.

The compiler CLI

FlagEffect
--no-checkSkip both type-checks (source RGE9002, generated RGE9001).
--scenes <dir>Validate every .json scene against the compiled prefabs, and import every Tiled .tmj map to <outDir>/scenes/<name>.scene.json.
--assets <dir>Check that every literal image, font, music and useSound path is a file in the folder (RGE1211).
--runtime <module>Where generated code imports the runtime from.

Output: a .ts and .ir.json per component, plus prefabs.ts and prefabs.json (only when every file compiled). CI fails if committed generated output is stale, so commit regenerated output.
