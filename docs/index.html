tseAuthoring guide and reference

New here? Getting started takes you from an empty folder to a packaged game.

Write games as components.

tse is a native-first 2D engine that you write in React-like TSX. There is no React and no virtual DOM: a compiler turns each component into a TypeScript class whose children are persistent instances, updated in place when state changes.

Component.tsxYour TSX: state, hooks, elements.
→
CompilerChecks the rules, lowers to an IR, emits a class.
→
Generated .tsOne class per component, committed next to an .ir.json.
→
PlayerRuns the frame loop, draws via raylib, reads input.

The mental model in five lines

  1. A component is a function: hooks, then exactly one return of JSX. It is compiled, never run as written.
  2. Its root is a built-in (Entity, Sprite, Game…), which the generated class extends.
  3. State is written directly (s.hp -= 1), and a handler reads its own writes; render sees what the frame committed. All of a frame's writes cause one render.
  4. Position is state: x={s.x} y={s.y} on any built-in (wrap a component in <Entity x y> to place it), usually driven by useMutable. Rows and columns are a <Flex>, anywhere. See Placing things.
  5. Each frame runs useInput, then useUpdate, then renders dirty components, commits structure and draws.

Game code goes in components, as in React. An enemy keeps its own hp in useMutable, walks in its useUpdate, takes hits in its collider's onCollisionEnter and tells its parent it died through a callback prop. A plain function in a .ts file is for what you would extract in React too: a pure calculation, a table, or something a search runs thousands of times.

Anything outside the supported subset is a compiler error (TSE####), never silently ignored. See Error codes.

A whole component

Coming from React

A component reads like React, and most of what you know carries over. What differs is that it is compiled, never run as written: the compiler turns it into a class whose children live as long as it does and are updated in place. The function body is a description for the compiler, which understands only the part of TypeScript it can turn into that class. Anything else is an error (TSE####) when you build.

What carries over

ReactHere
Function components, props, a props typeThe same. The props type is written in the parameter (({ hp }: { hp: number })) or declared in the same file.
An early if (!hero) return null;The same, at the top of the body: each if (…) return …; becomes a condition of the last return, and what follows it is worked out only when it did not return.
useState, updaters, batchinguseMutable: state you write directly (s.n += 1), with no setters or updaters. A handler reads its own writes at once, so s.n += 1 twice adds 2; render sees what the frame committed, and any number of writes cause one render per frame. A useState is an error whose message writes out the conversion in your names. Why: DESIGN.md, "State".
useMemo, useCallback, React.memoNot needed. The compiler knows what every value reads and does their job itself. A derived const that calls a function is worked out again only when what it reads changes. A render writes an element's values, or sends a child its props, only when a state or prop they read has a different value than at the last render. The component's functions are made once, so passing one down never re-renders anyone. See what a render does.
{cond && <X />}, {a ? <X /> : <Y />}, fragmentsThe same. A condition turning off unmounts.
{items.map((i) => <X key={i.id} />)}The same, with one inline arrow. Instances follow keys. key on a single element starts it over when it changes.
childrenchildren: Child in the props type, placed once as {children}.
Custom hooksThe same, written as use… functions; each call is expanded in place, so it gets its own state.
A Zustand storecreateGameState, read with useGame((s) => …) selectors and changed by actions.

What is different, and what to write instead

You would reach forWrite
useEffectThere is none, on purpose. Do the work where the change happens (an action, a handler), derive values, and use useMount, which may return a cleanup. See No useEffect.
onKeyDown, onClickKeys are polled: useInput((input) => input.pressed("jump")) every frame, and useUpdate((dt) => …) for the step. Clicks are onPress on a <Pointer> or <Flex>. inert and modal decide which subtrees hear the keys. See Who hears the keys.
style, CSS positioningx, y, rotation, z and opacity props, relative to the parent; <Flex> lays out UI.
useContextThe same: createContext in a .ts file, <Theme.Provider value>, useContext(Theme). What the whole game shares goes in useGame.
ref={…} on an elementNone: what is on screen follows state and props. A value to keep is a useMutable field.
Text in JSX: <p>Score {n}</p>Inside <Text>, as its children: <Text>Score {n}</Text>, or a component of your own that takes text (<Label>Score {n}</Label>, see Text wrappers). There is no text attribute.
A loop or push in the body to build a listThe same: statements in the body (loops, let, a local array) run again when what they read changes.

Three places code can go

Each place is checked by its own rules, and most "why is this an error" questions come from code written in the wrong one.

WhereMay holdFor

Plain .ts filesAny TypeScript.What you would extract in React too: tables and numbers, a pure calculation (a path, a target), the game state, and code a search runs many times (Kite's solver).

Hearth keeps its battle in components: Play keeps the gold, the lives and the lists; each Enemy, Tower and Shot keeps its own state and steps itself; they report up with callbacks and reach each other through collisions that carry data. Each is tested alone with @tsengine/testing. Kite keeps its movement in plain functions because a solver steps it thousands of times. See Plain functions.

When something goes wrong

Each component is written out as a class in generated/ (by tse dev, build and check; never edit it). You should not have to read it, because an error names your .tsx.

WhatWhere it points
A rule of the language (TSE1xxx)The line in src/, as you wrote it (custom hooks included).
A type error (TSE9001, TSE9002)The line in src/ of the element or hook; for one found in the generated code, where it was found is added in brackets.
An error thrown while the game runs (in the window, in a test)at Main.onInput (src/Main.tsx:14:3): the component's class, the method its hook became (onInput, onUpdate, onMount, render) and the line of that hook or element. Plain functions in .ts files show their own line.

When the game does something you did not expect

What you seeWhy, and what to write
My enemy does not see the playerTwo components share a value through their common parent: the player reports where it is with a callback prop, the parent keeps it in useMutable and hands it down (a prop, or context). It arrives one step later, every time. See Sharing state between components.
My collision is a step late (the hero is inside the wall before it stops)onCollisionEnter runs after the step's updates. Move with useBody: move stops at walls, and touching and overlapping answer in the same step.
The game is slow, or a frame takes too longUnder tse dev, open the inspector and press profile. It shows milliseconds per frame for each component and each phase of the frame, slowest first (the inspector).
A box is not where I expect, or I cannot see what a component holdsUnder tse dev, press F1 in the window to outline every box, its padding, every collider and pointer, and to name the box under the mouse. To watch the tree, a component's state and the game state as they change, open the inspector at the address tse dev prints. See Seeing inside a running game.
Something went wrong a few seconds ago, and is hard to make happen againUnder tse dev, press F2 and step back to it with the arrow keys. Fix the code and save, and the same moment plays again with the fix. F4 saves it for a test. See Rewind.
I am building a panel or a dialogue box, and must play to where it shows each timeGive it a stories file (its props, and game state for what it reads), and tse preview shows it on its own with hot reload; tse preview --screenshot stores pictures that tse check compares. See Previews.

tse turns this on for you (source maps next to each generated file, and Node's --enable-source-maps for the window and for tse check's tests). A packaged game, and the Rust host (--engine quickjs), do not map yet: their errors name the bundled game.js.

The compiler CLI

FlagEffect
--no-checkSkip both type-checks (source TSE9002, generated TSE9001).
--scenes <dir>Validate every .json scene against the compiled prefabs, and import every Tiled .tmj map to <outDir>/scenes/<name>.scene.json.
--assets <dir>Check that every literal image, font, music and useSound path is a file in the folder (TSE1211).
--runtime <module>Where generated code imports the runtime from.

Output: a .ts and .ir.json per component, plus prefabs.ts and prefabs.json (only when every file compiled). CI fails if committed generated output is stale, so commit regenerated output.
